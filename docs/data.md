# Warden's data

What Warden stores, whose it is, where it lives, how long it's kept, how it's deleted, and what leaves the
machine. It's written for someone who will run Warden, or trust it with their Team's data. The threats against
this data, and how each is met, are in [`threat-model.md`](threat-model.md).

**Built or designed.** Every row says which. **Built** means the code exists and has a test, with the slice or
spec that built it. **Designed** means it's decided but not built yet, with the spec that will build it. A
designed row is a plan, not a guarantee. Slices are the foundation spec's (#1): slice 1a is #4, slice 2 is this
document. The Guard, Patch and Vouch specs come after the foundation.

Where this document and an ADR disagree, the ADR wins.

## Retention and deletion

- **Agent events** are kept only until their Agent session is judged, and at most 7 days in the live database.
  A daily job deletes the rest (designed, Guard spec).
- **Backups:** Cloud SQL keeps 7 automated backups, one a day, and 6 days of point-in-time recovery logs (built:
  slice 1b-ii, the setup script, #16). **So an Agent event lasts at most 15 days in any form:** up to 7 days live,
  up to 1 more until the daily delete job runs, then up to 7 days in a backup taken before it was dropped.
- **The preview database** holds seeded data, and the Repo Assets and Findings of repos the owner links on a preview
  (#275), never real Agent events or a Real-world run's data. Kept until the next reseed.
- **Kept for the life of the Team:** Agent session records, Findings with their masked evidence and hash, Status
  history, Role history and Vouch's review log. They're the audit evidence (ISA2027 5.2.4, that logs are checked;
  4.2.1, that access rights are reviewed).
- **Deleting a Team:** an Admin deletes the Team's data. Its database rows go at once, its hook token rows among
  them, its objects in Cloud Storage go at once, its Agent sessions and events among the rows (its pseudonym key is derived from Warden's, so there is none of its own to destroy), and its Clerk Organization is deleted. Point-in-time
  recovery logs age out within 6 days, and backups within 7. The deletion job itself is **not yet planned**: no
  spec holds it yet (an open question below).
- **Team deletion isn't available yet** (until #6). Nobody can delete a Team today, from Warden or from Clerk:
  Organization deletion is turned off in Clerk through `adminDeleteEnabled`, for the instance (the setting "Allow
  members to delete this organization", which new Teams take) and on each existing Team (#70), not through the
  `org:admin` role's permissions. So the Team switcher's Manage screen offers Leave Team and no delete. Deleting
  only the Clerk Organization would leave every Warden row for the Team behind, so the delete stays off until #6
  deletes both together.
- **A person leaving:** history keeps their Clerk user id, never their name or email. The dashboard reads names from
  Clerk when it shows them. Once Clerk deletes the person, history shows "former member".
- **Cloud Logging:** Warden keeps the `_Default` bucket's 30 days. Every log line Warden writes passes through the
  redactor built in slice 1a (#4). Logs never hold an Agent event's content, a hook token, a secret value or a
  session token.

## What leaves the machine

Each outside service, what Warden sends it, and when.

- **Clerk:** identity and membership. When a person signs in, Clerk holds their name, email and sessions; Warden
  sends Clerk the Clerk Organization changes an Admin makes (invitations, `org:admin` for a Warden Admin). Built in
  part (slice 1a, #4: sign-in; slice 5b, #30: the Admin sync, a person's user id, Organization id and new Clerk role,
  sent when they're made Admin or stop being one, when their current Role is set again, and when someone Clerk calls
  `org:admin` joins as a Member; #43: the Organization switcher in the header, Clerk's own component, which sends
  Clerk the person's choice of Team, and a new Team's name, from the browser).
- **OpenRouter:** the redacted Agent events and repo text the Judge reads, and nothing else, once per Judge call
  (built: the call, #443; started on each `SessionEnd` the hook endpoint stores, #444).
  - **Before the first Judge call,** Warden's operator (whoever runs Warden) sets its OpenRouter account, on its privacy settings page
    (openrouter.ai/settings/privacy), to refuse providers that train on or keep prompts:
    - the training settings for paid and for free models are off, so OpenRouter won't route to providers that train;
    - Zero Data Retention is enforced for every model group (Anthropic, OpenAI, Google and "All other models"),
      with "ZDR only" rather than "Allow Safety Retention";
    - "OpenRouter Use of Inputs/Outputs" and "Private Input & Output Logging" stay off (both are off by default).
  - Each Judge call also asks for the same per request, with `provider: { "zdr": true, "data_collection": "deny" }`,
    so a changed account setting can't quietly widen it.
  - **The spending limit** is the OpenRouter key's $15 cap, set at OpenRouter. Under it (built, #481): a limit of
    $1 a day (UTC) per Team, checked against the spending ledger as each paid call's assumed cost is reserved in it,
    so a Team at its limit gets no call and its session stays unjudged with its events; a budget of 2 calls per Judge
    run (the call, and one retry when it times out, loses its connection, or answers 429 or 5xx); at most about 30,000 input tokens per call, the session's last events kept when it's longer; and
    one Judge run per session at a time (see the threat model, J5).
  - **The local-model option** for the Judge (a secure default) is built (#461): when a Team's Admin sets its own
    model (`PUT /api/judge/model`), the Judge sends the same redacted events to that model's URL instead, with no key,
    and sends nothing to OpenRouter. Clearing it puts the Team back on OpenRouter.
- **Langfuse:** traces of Warden's own model calls. A Judge call's trace sends metadata only (model, tokens, cost,
  timing, outcome), never its input or output, so judge-then-drop holds there too (designed, Guard spec).
- **GitHub:** when an Admin links an installation (built, #146), the code and verifier from their GitHub sign-in and
  the app's client secret go to GitHub once for a user token, which lists the installations the Admin can reach and
  the repos they can read in the one linked; GitHub's answer granting the App an installation token gives its
  permissions, and that token is never used. Both tokens are dropped after the one link. In a Guard Scan (built,
  #168, #188), the Scan Job signs as the app with its private key, never its client secret, and asks for one
  installation token per repo, scoped to that repo and to contents read; with it, it streams the default branch's
  archive from GitHub in memory, never writing it to disk. The token is dropped after the repo, and the archive after
  the Scan; files past the archive's limits (too large, binary, not UTF-8, a link) are skipped unread. Linking a
  write-app installation (built, #295) makes the same calls through the write app's own client id, secret and key,

  default branch. The token is dropped after the request; only the PR's URL, number and branch are stored.

  sent, nor the name of a server's package whose runner is pointed at another registry or index by its options or

- **CVE data:** none. Warden makes no outside call for CVE data: nothing is fetched from NVD, CISA KEV, EPSS or OSV.

  #101, #112).
- **Vouch:** none. Vouch makes no model call and no outside call: the Catalogue ships with Warden, in the server

## Data minimisation, and Warden never ranks people

The owner's rules for what Warden keeps about people and their work:

- **Redact on arrival, always,** at every Privacy tier. That includes the developer's home folder name in `cwd`,
  `transcript_path`, and every path in the tool input and tool output, which would otherwise name the person
  (built, #184: "The Privacy tier", below, says what's masked).
- **Safeagents scrubs on the laptop** where it runs, before events leave (designed, Guard spec).
- **Judge, then drop.** Agent events are deleted once judged (built, #443, started on each `SessionEnd`, #444), and
  never kept past 7 days (designed, Guard spec slice 8).
- **A flagged session's Finding keeps only** the masked events the Judge used, and a SHA-256 hash of the redacted
  events it read, in order. The hash is of the redacted text, not the raw text, so a short secret can't be confirmed
  by guessing it and hashing (designed, Guard spec).
- **Evidence never holds a secret's value:** path, line, type and a mask only (built, slice 6, #11, Finding v1).
- **Developers are pseudonymous** unless an Admin turns names on for the Team (designed, Guard spec).
- **Warden has no per-developer score, ranking or leaderboard,** and no view that sorts people by their Findings
  (designed: every dashboard spec keeps to it, from slice 9 on).

## The pseudonym

An Agent session names a pseudonymous developer, not a person (built, #183).

- **How it's made:** `HMAC-SHA256(team key, developer identifier)`, as 64 lower-case hex digits. There is one
  Warden key, `WARDEN_PSEUDONYM_KEY` (32 bytes, as 64 hex digits), and each Team's key is derived from it with the
  Team's id: `HMAC-SHA256(Warden key, Team id)`. The identifier is the `X-Warden-Developer` header's first 256
  characters; a missing or empty header, or the literal `$USER`, gives no pseudonym. The header's value is never
  stored or logged (#183). Without the key, the hook endpoint answers 503 and stores nothing.
- **Where the key lives:** one copy per service, in Secret Manager: `warden-pseudonym-key` for the live service and
  `warden-preview-pseudonym-key` for the owner previews, each made once by the setup script, read only by that
  service's account and never rotated (#185). Locally, the developer's own key is in the keyring (README.md, "Local
  setup"). The three are apart, so pseudonyms from one never match another's.
- **Deleting a Team:** a Team's key can't be destroyed on its own, as it's derived from Warden's. Its Agent sessions
  go with the Team, so no pseudonym of it is left to match.
- **What that gives:** the same developer gets the same pseudonym within a Team, and a different one in another
  Team. Someone with database access but without the key can't reverse it by guessing names and hashing them.
- **The developer identifier:** Claude Code's `http` hook body carries **no** developer identifier. Its common
  fields are `session_id`, `prompt_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`, and
  `agent_id` and `agent_type` for a subagent; none of them names the person. The hook can add request headers whose
  values come from environment variables on the laptop, but only variables listed in the hook's `allowedEnvVars`
  (and, in managed settings, `httpHookAllowedEnvVars`). So the identifier has to come from such a header, set in the
  managed settings. It's `$USER`, sent in the `X-Warden-Developer` header, with `allowedEnvVars: ["USER"]` on each
  hook (#100, question 3; built in #154). How it's tied to a Clerk user when an Admin turns names on is still
  **open**: the Guard spec leaves names-on out (threat model Q1). The value is whatever the laptop's environment says, so it identifies a developer
  only as far as the laptop is trusted.

## The Privacy tier

How much of an Agent session's content the hook sends to Warden, set per Team by an Admin. Built: the tier,
stored per Team, and the managed settings an Admin reads from `GET /api/hook` (Guard spec slice 9a-ii, #154). The
block's events: at Metadata and Details, `PostToolUse`, `PostToolUseFailure` and `SessionEnd`; at Content, also
`UserPromptSubmit`. It sends no `SessionStart`, because Claude Code runs only `command` hooks for it and skips an
`http` one (#465); a session's record starts at its first event instead. The endpoint still stores a `SessionStart`
that arrives (from an older block), through the same tier filter and redaction. The block leaves out only
`UserPromptSubmit` below Content: its `PostToolUse` and `PostToolUseFailure` hooks run at every tier, and Claude Code
posts each hook's whole JSON input, so every tier still sends the tool events' full input (`tool_input`) and output
(`tool_response`) to Warden. Built (#184): the filter on arrival, which applies the tier, and Warden redacting what
arrives, whatever the tier.

- **Metadata:** tool names and outcomes. Kept: `hook_event_name`, `tool_name`, `tool_use_id`, `permission_mode`,
  `agent_id`, `agent_type`, `source`, `reason` and `model`, each only as a string of at most 256 characters with no
  NUL and no lone surrogate (#183). The same rule holds for these fields at every tier.
- **Details (the default):** also commands, file paths and URLs. Kept: `cwd` and `transcript_path` when each is a
  string, and from `tool_input`, when it's an object, only the keys `command`, `description`, `file_path`, `path`,
  `notebook_path`, `url`, `pattern` and `glob` whose values are strings (no `tool_input` when none is). Never
  written or fetched content (`content`, `old_string`, `new_string`, `edits`, `new_source`, a tool's `prompt`), nor
  an MCP tool's other keys.
- **Content:** also tool output and prompts. Kept: the whole `tool_input` and `tool_response`, whatever their JSON
  type, and `error` and `prompt` when each is a string.

Every other field is dropped. The bounds at Details and Content (#184):

- **Size:** no bound per field beyond the endpoint's 1 MiB body limit, so a long command is kept whole and padding
  can't hide what it does.
- **Depth:** a field nested more than 64 levels deep (objects and arrays) is dropped whole.
- **What Postgres refuses:** each NUL and each lone surrogate, in every string and object key at any depth, becomes
  U+FFFD; the rest of the value is kept.
- **Objects:** a `__proto__` key is kept as an ordinary key and never sets an object's prototype.

**Redaction on arrival (built, #184).** What the tier keeps is redacted before it's stored, at every tier: every
string value and every object key, at any depth, in this order.

1. **The home folder becomes `~`:** `/home/<name>`, `/var/home/<name>`, `/Users/<name>` (also after git-bash's `/c`
   at a path's start, or WSL's `/mnt/c`) and `<drive>:\Users\<name>` (also after a long path's `\\?\`), in any case (macOS ignores it),
   with `/`, `\`, doubled or JSON-escaped separators, wherever the path is in the string: a command, straight after a
   flag (`-I/home/<name>`), deeper in another path, inside or after any URL (`file://`, `vscode://`, `ssh://`, and a
   web URL's own path, `https://example.com/home/x`, too). `<name>` runs to the next separator, whitespace, quote,
   shell operator or a URL's `?`, `#`, `&` or `=`, so a query after it is still masked. Claude Code's encoded project folder after `.claude/projects/` that starts with an encoded home
   folder (`-home-`, `-var-home-`, `-Users-`, `C--Users-`, in any case) becomes `~` whole. The developer's name
   elsewhere (a shell prompt, `whoami` output) isn't masked.
2. **Guard's nine secret types** (`maskSecrets`, over the patterns the secret Rules use) become their mask: the
   first 4 characters, then 8 `*`. Placeholders are left as they are. A private key is masked from its `BEGIN` line
   through its matching `END` line, or to the string's end.
3. **The log redactor's patterns:** Bearer tokens, JWTs, `sk_test_` keys, a Postgres URL's password and URL query
   values.

Two keys of one object that redact to the same text are both kept, the later one numbered (`~/a`, `~/a (2)`), so no
value is lost.

Claude Code's hook sends every field of each event it's set for: a tool event always carries the tool's input
(its command, path or URL), and its result carries the tool's output. So the tier is kept in two places: the
managed settings send only the events the tier needs (prompts only at Content), and the endpoint drops every field
above the tier before anything is stored. At Metadata and Details, content above the tier still leaves the laptop
and is dropped on arrival.
